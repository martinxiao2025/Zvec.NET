# 六类任务执行手册（playbooks）

执行者（task-executor）按任务「类型」路由到对应手册。共同要求（所有类型）：

1. 开工前必读：项目 `AGENTS.md` → `.agents/index.md` → `.agents/memory/MEMORY.md` 索引筛相关条目 → 任务文档
2. 方案先写入任务文档 §2（分析与设计），再动手改代码
3. 执行全程实时追加任务文档 §3 时间线（`| 时间 | 动作 | 详情 |`），**禁止事后凭记忆补写**
4. 构建与测试命令以项目 `AGENTS.md` 为准；提交前必须全量测试绿
5. 完成标准：自测通过 + 任务文档 §2/§3 完整 + 结论草稿（§5）就绪，交审核

## feature（新功能）

1. 理解需求：从描述与验收标准提炼「做什么/不做什么」，边界不清时在文档中列出假设
2. 定位：依据 index.md 找到相关模块与测试位置；新文件遵循项目既有目录约定
3. 设计：§2 写明方案要点、涉及文件清单、对公共 API 的影响
4. 实现：小步提交粒度的修改；遵循项目代码规范（AGENTS.md）
5. 自测：构建 + 针对性测试 + 全量测试；新功能必须附带测试（除非纯文档）

## bug（缺陷修复）

1. **复现优先**：先按描述复现或给出无法复现的证据（无法复现→反馈编排者，不得盲修）
2. 定位根因：追到产生问题的源头，禁止只修表象；根因与排查路径写入 §3
3. 最小修复：改动范围最小化；顺手重构需单独开 refactor 任务
4. 回归测试：针对根因新增至少 1 个失败用例（修复前红、修复后绿），写入测试工程
5. 验证：全量测试绿，确认未破坏相邻行为

## test（补充测试）

1. 选择目标：公开 API 中未覆盖/覆盖薄弱的路径；参考 index.md 的测试位置
2. 设计用例：正常路径 + 边界值 + 异常路径（非法参数/空值/极值）；非确定行为（时间/随机/网络）须可注入或跳过
3. 风格一致：命名、断言风格、文件位置与现有测试保持一致（先读相邻测试文件）
4. 运行：新增用例单独跑一遍 + 全量跑一遍，结果摘录进 §5

## docs（文档）

1. 定位插入点与现有章节结构，风格（标题层级/语言/表格 vs 列表）与原文一致
2. 内容必须从代码/现有文档验证，**禁止臆造 API 或行为**；不确定的写「待确认」并留在 §5 遗留
3. 链接有效：新加的相对链接逐一核对目标存在
4. 验证：文档类任务也须跑一次构建，确认未误改代码

## refactor（重构）

1. 前提：行为不变——先确认现有测试覆盖足够，不足则先补测试（可在 §2 说明）
2. 小步进行：每步后构建+测试绿再继续；公共 API 变更须在 §2 显式声明并说明替代方案
3. 不夹带功能变化；发现 bug 记入 §5 遗留，另开 bug 任务

## chore（杂务）

1. 确认目标无引用（删除文件/依赖前全局搜索引用）
2. 执行后构建 + 全量测试验证
3. 涉及配置/脚本变更时，同步更新受影响文档
